# Core 대기열·동시성 검증 결과

## 목적

한정 상품에 주문이 집중될 때 다음 두 가지를 확인했습니다.

1. Queue가 주문 API와 DB transaction 진입 후보를 줄이는가
2. Queue와 Direct 모두 재고 정합성을 지키는가

## 실험 조건

| 항목 | 값 |
| --- | ---: |
| 사용자 | 5,000명 |
| 요청 도착률 | 초당 500명 |
| 지속시간 | 10초 |
| 초기 재고 | 100개 |
| Queue active window | 40명 |
| DB connection pool | 10개 |
| Tomcat max threads | 200개 |
| pre-allocated VU | 1차 1,000 / 2·3차 2,000 |
| max VU | 3,000 |

Queue와 Direct는 같은 조건에서 실행했으며, 각 실행 전에 PostgreSQL과 Redis를 초기화했습니다.

## 핵심 결과

dropped iteration 없이 5,000명을 모두 처리한 2차 실행을 대표값으로 사용했습니다.

| 지표 | Direct | Queue |
| --- | ---: | ---: |
| 완료 사용자 | 5,000명 | 5,000명 |
| 주문 API 진입 | 5,000건 | 104건 |
| 생성 주문 | 100건 | 100건 |
| 정상 비즈니스 거절 | 4,900건 | 4,900건 |
| 예상하지 않은 오류 | 0건 | 0건 |
| dropped iteration | 0건 | 0건 |

Queue는 동일한 100건의 주문 정합성을 유지하면서 주문 API 진입을 97.92% 줄였습니다.

```text
Direct: 사용자 5,000명 모두 주문 API 진입
Queue:  4,896명은 대기열에서 품절 처리, 104명만 주문 API 진입
```

Queue에서 주문 API에 진입한 104명 중 100명은 주문에 성공했고, 경계 시점의 4명은 재고 부족으로 정상 거절됐습니다.

## 반복 결과

| 실행 | Direct 주문 진입 | Queue 주문 진입 | 감소율 | Direct dropped | Queue dropped |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1차 | 4,843건 | 109건 | 97.75% | 157건 | 770건 |
| 2차 | 5,000건 | 104건 | 97.92% | 0건 | 0건 |
| 3차 | 5,000건 | 121건 | 97.58% | 0건 | 273건 |

주문 API 진입 감소율은 세 번 모두 97.5~97.9%로 비슷했습니다. 반면 Queue는 대기 시간이 길어진 1·3차 실행에서 VU가 부족해 일부 iteration이 실행되지 않았습니다.

## 응답시간과 비용

동일하게 5,000명을 완료한 2차 실행의 결과입니다.

| 지표 | Direct | Queue |
| --- | ---: | ---: |
| 주문 API p95 | 2,909.15ms | 2,985.75ms |
| 주문 성공 흐름 p95 | 2,471.30ms | 3,460.60ms |
| 전체 흐름 p95 | 2,911.05ms | 5,172ms |

Queue는 DB 진입을 줄였지만 사용자에게 대기 과정과 추가 요청을 발생시켰습니다. 따라서 이번 실험에서 Queue는 응답시간 개선 수단이 아니라 DB 보호를 위한 admission control로 해석합니다.

## 정합성 확인

마지막 Direct 실행 후 DB를 확인한 결과입니다.

| 항목 | 결과 |
| --- | ---: |
| 초기 재고 | 100개 |
| 최종 재고 | 0개 |
| 생성 주문 | 100건 |
| 주문 수량 합계 | 100개 |
| 중복 `checkoutToken` | 0건 |
| 구매 제한 위반 | 0건 |
| 서버 ERROR | 0건 |

Direct만으로도 PostgreSQL의 조건부 재고 차감과 제약 조건을 통해 판매 정합성은 유지됐습니다.

## 결론

- PostgreSQL은 최종 판매 정합성을 담당합니다.
- Redis Queue는 정합성을 위한 필수 요소가 아니라 집중 주문 시 DB 진입을 제한하는 보호 장치입니다.
- Queue는 일반 상품에 항상 적용하지 않고 트래픽이 집중되는 LIMITED 상품에만 조건부로 사용합니다.
- 현재 구현은 Queue 대기시간과 VU 사용량의 편차가 있으므로 응답시간 개선 효과는 주장하지 않습니다.

이번 실험에서 확인한 핵심 효과는 다음과 같습니다.

> 5,000명이 10초 동안 접근한 상황에서 판매 수량 100건을 정확히 유지하면서 주문 API와 DB transaction 진입 후보를 5,000건에서 104건으로 97.92% 줄였다.
